# 2026-11-10 인하우스 성능 분석 실험 기록

인하우스 스캔에서 자동 라벨(`toothseg-pureptv3/1`)이 기대보다 나쁜 이유를 찾은 실험들이다.
앞부분(E1~E9)은 치아 **번호**와 색을, 뒷부분(E10~E16)은 번호를 빼고 **치아 instance를 제대로 찾는지**를 본다.
E15~E16은 후처리를 추론 서버에 넣으면서 한 실험과 검증이다.
스크립트는 `scripts/`, 출력은 `results/`에 있다. 모델과 데이터는 바꾸지 않았다. 바꾼 코드(학습 설정, 추론 서버 후처리)는 맨 아래 "코드 변경"에 있다.

## 지표

- **번호 (E1, E7):** 치아/잇몸 F1, 위치(좌우 무시) 정확도, 좌우 정확도, FDI 정확도. 모두 정점 단위다. 치아 단위 번호 정확도도 쓴다.
- **instance (E10~E16):** 번호는 무시한다. 정답 FDI 하나가 instance 하나이고, 예측 instance는 라벨 영역의 mesh 연결 성분이다. E16, E16b의 "DDH 기준"은 예측도 같은 FDI 하나를 instance 하나로 본다(DDH가 저장하는 방식).
  - 면적 가중으로 잰다. 정점 면적 = 닿은 삼각형 넓이 / 3. 공개 데이터는 면이 없어 정점 kNN(8) 그래프에 정점 수로 잰다.
  - F1@50, F1@75: IoU로 1:1 매칭(Hungarian)하고 IoU ≥ 0.5 / 0.75를 맞음으로 본다.
  - mIoU: 정답 치아마다 가장 잘 맞는 예측의 IoU를 평균한다.
  - merge: 예측 하나가 정답 둘 이상을 각각 30% 넘게 덮은 경우의 수.
  - split: 정답 하나를 예측 둘 이상이 각각 20% 넘게 덮은 경우의 수.
  - 경계 오차(mm): 정답 경계에서 예측 경계까지 거리(GT→P, 놓친 경계)와 그 반대(P→GT, 헛 경계). 치아-잇몸 경계(margin)와 치아-치아 경계(inter)를 따로 잰다.

### E5 크롭과 augmentation — `crop_rate.py`, `aug_check.py`

ToothSegLoader 기본값으로 크롭 방식마다 실제 적용률을 쟀다(데이터셋마다 30개).
teeth3ds, poseidon3d, cbct_ios_fusion은 거의 100% 적용된다. 3d_iosseg는 점이 8천 개 정도라 bridge 0/30, quadrant 1/30, half 12/30만 적용됐다(남는 점 3,000개 하한).

`--crop-p 0.5`로 학습 샘플 200개를 뽑았을 때:
- 46%에서 치아가 빠졌다(부채꼴 크롭은 치아를 하나도 지우지 않을 때가 있다).
- 크롭 뒤 중심 오차는 4e-6 mm.
- 교합면 축은 매번 달랐다(SO(3)).

### E17 배포 모델이 본 학습 입력 — `aug_audit.py` → `results/aug_audit.log` (GPU 없음)

사용자가 하프·브릿지에서 instance 분할이 나쁘다고 했다(이후 풀아치도). 그래서 학습 augmentation을 다시 봤다.
배포 모델 `toothseg-pureptv3/1`은 크롭 50% 설정을 넣기 전의 첫 학습이다(crop_p 0.35). 데이터셋마다 40개씩 `train_recipe_cpu`를 돌리고, 남은 치아 비율로 무엇이 됐는지 셌다.

| 남은 치아 | 배포 모델 (crop_p 0.35) | 지금 기본 (crop_p 0.5) |
|---|---|---|
| 85% 이상 (전악) | **83%** | 69% |
| 6개 이상 (부분 악궁) | 6% | 10% |
| 5개 이하 (bridge급) | 11% | 21% |

- 3d_iosseg는 크롭이 거의 적용되지 않는다(전악 98%). 점이 적어 남는 점 하한(3,000)에 걸린다.
- **교합면 방향이 데이터셋마다 다르다.** 치아 법선 평균의 주축은 teeth3ds z 40/40, cbct_ios_fusion z 40/40, poseidon3d z 30/40 · y 10/40, 3d_iosseg y 40/40이다.
  - wedge 크롭(크롭의 25%)은 회전 전에 xy 평면의 각도로 자른다. 그래서 3d_iosseg와 poseidon3d 일부에서는 악궁 부채꼴이 아니라 엉뚱한 단면을 남긴다.
  - segment 크롭(bridge 2~5개 / quadrant 치아의 25~50% / half 45~60%)은 치아 순서를 따라 고르므로 방향과 무관하다.
- 교합면 기준 평면으로 1/2, 1/3을 나누는 크롭은 따로 없다. half와 quadrant가 치아 수로 비슷한 범위를 덮을 뿐이다.
- **SO(3):** 매 샘플 적용된다. 회전 뒤 교합면 방향의 z성분이 고르게 퍼진다(|z| 평균 0.45~0.52, 균일하면 0.5). 크기 ±10%와 jitter 0.05 mm도 함께다.
- **중앙 정렬:** 매 샘플 적용된다. `ToothSegDataset.__getitem__`이 크롭과 회전 뒤 voxel 대표점의 평균을 뺀다(E5: 오차 4e-6 mm). 회전은 원점 기준 선형 변환이라 "중심 → 회전"과 결과가 같다.
- 결론: 학습 샘플의 83%가 전악이었고, 반악궁 크기의 입력은 6%뿐이었다. 부분 스캔이 약한 이유 중 하나다.
  - 다만 segmentation3d instance_ios도 같은 기본값(crop_p 0.35)으로 학습했는데 공개 크롭에서 F1@75 0.99다(E12).
  - 그래서 크롭 노출만이 원인은 아니다. PurePTv3가 위치 라벨로 instance를 나누는 구조가 더 큰 원인이다(E13~E15).
  - 사용자도 ToothSegNet instance는 치아 경계가 거의 모든 경우에 맞았고, 번호는 중요하지 않다고 했다.

- `dental-ai` `AugmentationParams`에 `colour_edge_mm`, `colour_edge_width_mm`, `colour_drift_scale`, `synth_colour_cpu`에 경계 전이 모드를 넣었다. 기본값(None)은 예전 동작 그대로다. 커밋하지 않았다.
- **추론 서버 `inference-server/` (개선 포인트 1~3, E15b의 기준):**
  - `toothseg.py` 어댑터 `toothseg17`의 후처리를 바꿨다.
    - TTA: 자세 수는 `DDH_AUTOLABEL_TTA`, 기본은 GPU 8, CPU 1. 회전은 segmentation3d `tta_rotations`와 같은 행렬이다.
    - 정점 확률은 가까운 대표점 5개의 거리 가중 평균이다.
    - 위치는 좌우 확률을 더한 값으로 고른다.
    - 5 mm² 조각을 정리한다.
    - instance를 먼저 만든다. 넓은 중절치만 정중선에서 나누고, 사분면은 instance마다 정한다.
    - 같은 번호의 치아가 둘 이상이면 경고한다.
  - `decide_quadrant`는 17-class 대신 위치(0..8)를 받는다. "single"일 때 쓸 모델의 좌우(`model_second`)는 따로 받는다.
  - `app.py`는 요청의 `faces`(삼각형)를 받아 검사한다.
  - 단위 테스트 22개는 이미지 빌드에서 돈다.
  - 바꾸기 전 파일은 `scripts/baseline_inference/toothseg.py`에 있다.
- **dashboard-server `app.py`:** 자동 라벨 요청에 mesh 삼각형(`faces`)을 함께 보낸다.
  - 삼각형만 있으면 plyfile의 고정 길이 목록 + mmap으로 읽는다(255k 정점에 50 ms 이하). 삼각형이 아닌 면이 있거나 포인트 클라우드면 보내지 않는다.
  - 원본 인하우스 PLY 42개를 DDH 방식으로 정규화해, plyfile의 느린 경로와 같은 면이 나오는지 확인했다.
- `docker-compose.yml`: inference-server에 `DDH_AUTOLABEL_TTA`를 넘긴다.
- 문서: `inference-server/README.md`, `docs/Models.md`, `dashboard-server/docs/TechSpec.md`.
- 어느 것도 커밋하지 않았다. `inference-server/`는 아직 git에 들어 있지 않다(untracked).

## 한계와 주의

- 인하우스 정답이 12개(치아 88개)뿐이다. 번호 라벨에는 오류가 있어 보이고, instance 경계는 그대로 썼다.
- E10c의 경계 공유 기준, E10b의 깎기 폭은 같은 12개에서 고른 값이다. 다른 스캔으로 확인해야 한다.
- 공개 데이터는 면이 없어 kNN 그래프와 정점 수로 쟀다. 인하우스(면, 면적 가중)와 숫자를 직접 비교하지 않는다.
- segmentation3d semantic(S2)은 Teeth3DS만으로 학습한 모델이고, instance_ios는 PurePTv3와 같은 데이터로 학습했다.
- `results/instance_pred.npz`에는 스캔마다 정점별 instance 번호(int16)가 있다. 키는 `<스캔>__<방법>`이고, `GT`도 함께 들어 있다.
